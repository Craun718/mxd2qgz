## 对象流、对象体和跨流上下文

新鲜反编译 `SystemCore!0x7ffcf7a0` 将传入流写入对象的流字段，随后只对新流 AddRef、旧流 Release；函数体未清空或重建对象表。读入口 `0x7ffcff70` 从当前底层流读取 16 字节 CLSID 和 4 字节键：键命中时取已有对象并返回，不执行该对象的 Load；未命中时创建 COM 对象、登记键，再调用普通持久化 Load，或建立 VariantStream 包装后调用 Variant 持久化 Load。写入口 `0x7ffcf7e0` 对新对象写 CLSID、插入写表、写当前键并递增计数器，然后调用对象 Save；已见对象写既有键并不写对象体。由此可确认：同一 ObjectStream 的流切换保留会话上下文，体的消费边界由被分派对象的 Load/Save 决定，通用对象头没有体长字段。

该结论闭合了跨流共享的是何种状态，但没有闭合全部对象体。对未知类、尚未覆盖的类或失败的 Load，不能仅凭对象头推算体长并跳过；因此 TODO 95 仍不宜勾选为“完整对象体已闭合”。现有按类读取器的已确认前缀仍可作为其各自范围内的证据，不代表所有类均已解析。

## VariantStream 对象分支与引用表

10.1 VariantStream 的 VARTYPE 9/13 对象分支进入 AfCore `LoadObject`；SystemCore 的 ObjectStream 新对象分支也会为 Variant 持久化对象建立 VariantStream 包装。实际对象体仍由具体类的 Variant Load 消费，没有通用长度。引用表归属取决于传入的流对象及其接口查询/包装上下文；VARTYPE 9 或 13 本身并不编码“此处一定是 ObjectStream 键回引”。现有 10.1 `LoadObject` 静态记录也指出，Variant `LoadObject` 的包装/尾部辅助函数尚未完全定性；10.8 曾记录的 QI 上下文分支不能未经 10.1 证据逐项映射就直接外推。

因此 TODO 99（对象体）和 100（引用表）保持开放。完成它们至少需要闭合 10.1 的 `LoadObject` 包装和每种实际流组合的接口传播，并逐类取得对象体边界；目前没有可控的 Variant 对象 MXD 样本或运行观察。

## SimpleSaveObject 委派链

既有 10.1 AfCore 研究将 `SaveObject`（`0x68a7b640`）追到 `StrmUtil::SimpleSaveObject(..., writeHeader=1)`（`0x68a7af70`）。普通 IPersistStream 分支写可选 CLSID 后直接调用 `IPersistStream::Save(stream, clearDirty)`，本身不写 ObjectStream 键；Variant 分支递归保存相应值，并以 VariantStream 包装分派。SystemCore 的对象写出槽 `0x7ffcf7e0` 则另外负责写 CLSID、键/回引，并调用具体对象 Save。两条路径职责可区分，但 SimpleSaveObject 通过 ObjectStream 专用查询/包装分支到达 `+0x40` 写槽的完整 QI IID、成功条件和槽位链尚未逐跳证明。

故 TODO 102 只能确认局部职责，整体委派链未闭合，保持开放。AfCore 本轮 fresh decompile 没有取得可用结果；不能以保存的旧伪代码冒充本轮新鲜证据。

## 重复键替换分支

新鲜反编译 `SystemCore!0x7ffd0950` 显示：当读表中键已存在时，函数直接用新对象指针覆盖节点对象指针并返回 1；该分支本身未见 Release 旧对象。新键则分配并插入节点。结合读入口：正常读取先查键，只有 miss 才创建并登记对象，所以常规读路径不会以已存在键再次登记。结合写入口：写侧按对象身份查写表，命中时写已有键后结束，不从正常保存路径再次插入该键。

这解释了静态调用路径中重复键分支为何不是普通加载/保存的常规路径，但不能证明所有异常/内部调用都不可触发，也不能代替用户要求的原生替换场景。TODO 112 要求触发并观察替换后对象及回引交互，必须有 ArcMap 原生运行场景；目前未具备，保持开放。
