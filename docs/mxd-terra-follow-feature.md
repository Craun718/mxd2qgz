## +0x1b4：读前释放和清零

1. Load 开头 `0x6f6e998a` 将第一个显式参数放进 EBX；版本有符号 `>8` 时，`0x6f6ea571..0x6f6ea585` 将 `EBX+0x1b4` 放入 ESI，调用 `0x6f6acc10`，再将其返回值作为输出地址传给 `LoadObject`，请求既有记录确认的 IEnvelope IID。版本 `<=8` 在此处跳过该处理，不能据此断言该槽的初值。
2. **新复核的助手行为**：`0x6f6acc10..0x6f6acc2c` 读取 `[ESI]`；非零时调用该指针虚表 `+8`（IUnknown 布局下为 Release）并清零；无论原值是否为零，随后把 `[ESI]` 写零并返回 ESI。于是进入读取前，旧引用会被释放且槽被清零；这发生在 `LoadObject` 返回成功还是失败之前。读取失败后只从此段可知 Load 检查负 HRESULT 并转错误路径，不能仅凭此段断言整个失败路径的最终对象状态。
3. 因此，[先前空间调用链](mxd-parse-agent-map-layer-spatial-20261117.md)中“Load 读入空标记后不会写 +0x1b4”的表述不准确：**读取之前已经清零，并可能释放旧引用**。通用空对象读取及输出地址的完整行为仍须结合对象流实现和运行证据审查；这里不把预清零等同于对所有异常输入或最终成员状态的证明。已知 Save 空指针的 16 零字节仍只是写侧机制。
4. 位移扫描也命中 `0x6f6f01a0`、`0x6f6f0670`、`0x6f6f0870`、`0x6f6f08e0` 等函数，但不能单凭 `+0x1b4` 将它们归到此槽：例如 `0x6f6f01b7..0x6f6f01c5` 先从参数算出减 `0x130` 的地址给助手，却从未经调整的参数 `+0x1b4` 取值；其接口基址和 Load 参数是否相同尚未证明。候选 setter `0x6f6f08e0` 的反编译还删去不可达块，不能据此宣称已找到该槽 setter 或行为。

这推进了 297 的**静态读前行为**，但不支持“成员总为空”或“无副作用”。仍需按接口子对象调整追到构造、赋值和释放路径，在已授权 ArcMap 10.1 上观察非空旧值、空标记、错误流等可控情形；不能用构造输入充当运行取证。

## +0x1f4：调用前条件和未命名接口边界

- `0x6f6ea845` 版本门为 `>=0xf`。在读取 `short +0x12e`、`int32 +0x1f0` 后，若 `+0x130` 非空，先调用其虚表 `+0x4c`，参数为 `+0x1f0` 地址；然后 `0x6f6ea8ae..0x6f6ea8bf` 对 `+0x1f4` 调用与上节相同的释放、清零助手，再请求 IEnvelope 并执行 `LoadObject`。这确立本段的先后次序，但不确立 `+0x4c` 的正式名称或副作用。
- `LoadObject` 返回负数时跳转错误处理；成功后 `+0x130` 为零则跳过该数据源接口链。非零时通过 `0x6f705d00` 查询 `{720A857D-45A9-4DBF-AA06-73715C654B01}`，其结果非空才继续；再由 `0x6f705db0` 在该接口上查询 `{89E86261-2B2D-45A7-BE01-64190DBC9BDB}`。从汇编 `0x6f6ea93a..0x6f6ea94b` 可见第二次查询后直接经返回指针的虚表 `+0x10` 调用，参数为当前 `+0x1f4`，没有在两者之间对该指针或 Envelope 参数作空检查。`0x6f705db0` 的汇编在 QI 负 HRESULT 时将输出置零；静态代码呈现这一潜在失败边界，但不能推断该组合在真实数据源中可达，或推断实际异常与恢复方式。
- 因而本轮只确认这是 Load 后传给特定接口方法的 IEnvelope，不足以把它命名为绘制范围、缓存范围或数据范围。还需识别两个接口、方法签名及具体数据源实现，追踪赋值/使用路径，并用具有可控图层和视图状态的 ArcMap 10.1 运行观察验证；静态 QI 和样本坐标不能代替运行观察。
