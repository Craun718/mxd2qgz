# 空间参考增量取证（2026-11-17）

本记录只记本轮新增或更正；既有布局及未闭合项见 [PCS/GCS 记录](arcmap-10.1-pcs-geometry-slots.md)。全部是静态证据和合成测试，未运行 ArcMap，不能替代实机验证。

## 对象身份与方法

目标为介质提取的 x86 Geometry.dll，SHA-256 `c57d154f207ee249adc69136574cf274771370ff93a15eb0be5682ce828f0d47`，与既有 VS_FIXEDFILEINFO 10.1.0.3035 身份记录一致；介质 Desktop 配置声明 10.1.3035，见 README。以 JDK 25 和独占 pyghidra 工程分析，另以 objdump 核对控制流。首次尝试因 JVM 使用 `/tmp` 导致空间不足失败；设置 `java.io.tmpdir` 到仓库独占目录后完成。未连接或修改共享 Ghidra 桥接工具 服务器。反编译及查询记录在 `temp/terra-integrate-sr/`，该目录为临时研究产物，不作为交付依据。

## 版本 2 域串及 PCS 垂向单位段

- PCS Load `0x719d343a..0x719d3452` 和 GCS Load `0x719beeca..0x719beee5` 都对版本与 2 做有符号比较，`jl` 跳过四串读取，即 **版本 >=2** 才进入 `0x719babf0`。这是对既有记录中“版本 >2”的更正；版本 2 并非仅 WKT。GCS 范围的另一判断在 `0x719bec60` 反编译中是 `2 < version`，仍为版本 >=3。原生有符号负版本的行为不等同本读取器，本读取器仍拒绝负位模式。
- PCS 的标志非零路径 `0x719d3481..0x719d34a8` 调用 `0x719ea140`，之后才进入精度段。读取器此前仅消费标志，会误把单位段当精度字段；现复用 GCS 的单位段读取，保留版本及原始文本，失败回滚游标。单位 WKT 的含义不由此推断。
- 原生 `0x719babf0` 对每串读 u32 长度和指定字节，写宽 NUL 到 `buffer + (length & ~1)`，再以 NUL 结尾构造 BSTR；奇数长度末字节会被覆盖，内嵌宽 NUL 也会影响所得 BSTR。`0x719bad00` 写 BSTR 字节长和字节。读取器有意保留完整原始字节而不模拟这些对象重建结果；业务名称和填充来源仍未闭合。

## GCS 守卫与槽位

- `0x719beca5` 在第一个 `AfStreamRead` (`0x719bece0` 附近) **之前**检查持久化接口 this+`0x98`，非零走错误 `0x80004005`/`0x1ca`。构造器 `0x719c345c` 在完整对象 +`0x2c` 安装持久化虚表，因此该成员是完整对象 **+`0xc4`**，并非旧记录的 +`0xac`；旧表格把守卫置于读 WKT 之后的顺序亦不准确。此处不推断失败后流和对象的其他行为。
- 构造器 `0x719c3091` 将 EBX 清零，`0x719c32a7` 写到对象 +`0xc4`；析构路径 `0x719c3985..0x719c3995` 非零时仅清零这一成员。QI `0x719bc4b7..0x719bc4e3` 对 IID `{3B219F24-D3FF-11D1-BC9B-0000F875BCCE}` 检查同一成员，非零返回 `0x80004002` 和空接口。同介质 esriGeometry.olb（SHA-256 `d45fb2105c869cda034fa80101cf2d0b932e08ea6f31eca8d4322fe7f7cd3e8e`）的 MSFT 类型记录将此 IID 定名为 IGeographicCoordinateSystemEdit，GeographicCoordinateSystem coclass 也直接声明该接口。由此确认非零成员同时拒绝持久化 Load 和对地理坐标系编辑接口的查询。成员类型及产生非零状态的路径仍待取证。
- slot 8 `0x719bf440` 取第二个栈参数并直接写入 `0x38`，返回 0，未见空指针检查；静态引用仅发现 GCS/PCS 两虚表项 `0x71a26838`/`0x71a29cec`。这不证明无间接调用，也不足以确定接口成员名或调用协议。

定向合成测试检查 PCS/GCS v2 四串边界、GCS v2 无范围、PCS 非零垂向段后精度对齐、逐字节截断回滚和限额；仅验证 Rust 读取器，不是原生运行结果。Unknown 四串业务名称、slot 8 名称、守卫置位来源及含义仍待进一步取证；GCS/Unknown 未在参考 MXD 中确认实例。ArcMap 10.1 和 QGIS 人工目视检查均未执行。

### PCS 与 GCS 域串的属性映射

用 objdump 复核同一份 x86 Geometry.dll 10.1.0.3035。Load 辅助函数
`0x719babf0` 按序装入独立结构的 `+0x04/+0x08/+0x0c/+0x10`，
Save `0x719bad00` 按相同顺序取值。PCS 从持久化接口 `+0x20`
传入该结构（`0x719d344e`），GCS 从持久化接口 `+0x8c`
传入（`0x719beede`）。

两类的 ISpatialReferenceInfo 都位于完整对象 `+0x18`，分别由
QI `0x719d0967` 与 `0x719bc485` 的 IID 比对确认。按同版
esriGeometry.olb TypeInfo 4 对位，PCS 使用虚表 `0x71a297ac`，
GCS 使用 `0x71a26614`。以下 getter 均取同一结构中的 BSTR。

| 流序号 | 结构偏移 | 属性 | PCS getter | GCS getter |
| --- | --- | --- | --- | --- |
| 1 | `+0x04` | Alias | `0x719d39b0` | `0x719bf520` |
| 2 | `+0x08` | Abbreviation | `0x719d3a00` | `0x719bf570` |
| 3 | `+0x0c` | Remarks | `0x719d3a30` | `0x719bf5b0` |
| 4 | `+0x10` | Usage（类型库参数拼写为 `useage`） | | |

辅助结构构造器 `0x719baaa0` 与 `0x719bab40` 用 AfCore
BString 构造器初始化四个空串。PCS 复制入口中的 `0x719d053d–0x719d0574`
将四个槽逐项复制。

同版类型库 TypeInfo 75 和 108 的 `+0x0c` 槽分别是
`IGeographicCoordinateSystemEdit::Define` 与
`IProjectedCoordinateSystemEdit::Define`。二者的前五个显式参数均为 BSTR，
依次是 Name、Alias、Abbreviation、Remarks、`useage`。

- GCS 主 QI 在 `0x719bc4b7` 比对编辑 IID，成功路径在
  `0x719bc530` 返回完整对象 `+0x28`。虚表 `0x71a26800` 的 Define
  为 `0x719c02d0`。其 `0x719c04db–0x719c0525` 路径采用 AfCore
  BString 赋值（IAT `0x71a102fc`），将四个非空指针参数分别写到
  `+0x04/+0x08/+0x0c/+0x10`。最后一个参数从 `[ebp+0x1c]`
  经局部变量 `[ebp-0x78]` 转入第四槽。
- PCS 主 QI 在 `0x719d08f9` 比对编辑 IID，成功路径在
  `0x719d0953` 返回完整对象 `+0x30`。虚表 `0x71a29c28` 的 Define
  为 `0x719d5d50`。其 `0x719d60a2–0x719d60e6` 以同一顺序赋值，
  最后一个参数从 `[ebp+0x1c]` 经 `[ebp-0x78]` 转入第四槽。

这两条 Define 路径确认第四串为 Usage，并确认四串可由编辑接口填充。
其他赋值入口仍待核查。ArcMap 10.1 和 QGIS 尚未人工验证。

### DefineEx 的域串写入路径

复核 Geometry.dll 10.1.0.3035 的同一组编辑虚表。TypeInfo 75 和
108 将编辑接口 `+0x10` 槽定名为 DefineEx，五个字符串参数使用 VARIANT
指针。GCS 的入口为 `0x719c0580`，PCS 为 `0x719d6140`。

两者先将临时字符串指针初始化为空，对字符串参数进行类型转换，
目标类型为 VT_BSTR。以 Usage 为例，GCS 从 `0x719c0703` 开始
检查参数，PCS 的对应入口为 `0x719d62d1`。转换及其他参数
准备成功后，GCS 在 `0x719c0b2d–0x719c0b30`，PCS 在
`0x719d670e–0x719d6711`，调用各自编辑虚表的 `+0x0c` 槽。
所以 DefineEx 通过 Define 写入同样的四条持久化字符串。空参数、转换失败后的对象状态及保存结果仍待运行验证。

### PCS 创建关联 GCS 时的域串来源

Geometry.dll 10.1.0.3035（SHA-256
`c57d154f207ee249adc69136574cf274771370ff93a15eb0be5682ce828f0d47`）
的 PCS 延迟创建函数 `0x719d76d0` 从 PCS 的 +0x68 结构中
取 +0x14 的投影引擎句柄。它在 `0x719d772c` 调
`pe_projcs_geogcs`，并在 `0x719d7732` 调
`pe_geogcs_clone`。两个跳板可经 IAT `0x71a10c98`
与 `0x71a10d5c` 核对到 pe.dll 导入名。

`0x719d7739` 以克隆的引擎句柄和 `-1` 为参数构造
新的 0x28 字节辅助结构。构造体 `0x719bab40`
的 `0x719bab6d–0x719babb0` 使用同一个空字符串
常量初始化 Alias、Abbreviation、Remarks、Usage 四项；
`0x719babb8` 单独登记引擎句柄。随后
`0x719d776f` 把新辅助结构传给 GCS 构造器 `0x719c3330`。
GCS 在 `0x719c353b` 把该结构保存到自身 +0xb8，并在
`0x719c35bb` 增加其引用计数。因此关联 GCS 的四条域串
从空值初始化，PCS 的四条域串在这条路径上没有被复制。

这条静态证据仅闭合 PCS 延迟创建关联 GCS 的路径。其他
构造和后续属性填充入口仍待复核，尚未在 ArcMap 10.1 或
QGIS 中人工验证。

### WKID 工厂首次分配的域串

仍以 Geometry.dll 10.1.0.3035 为准。两条接受整数坐标系代码的
入口分别在 `0x719e103f` 和 `0x719e113f` 调用
`pe_factory_coordsys`（跳板 `0x719f336c`，IAT `0x71a10ab8`）。
它们通过 `pe_projcs_p` 区分坐标系类型，随后将代码交给
`0x719e1c40`（调用点 `0x719e10ae`、`0x719e11ae`）。
GCS 入口将该函数返回的辅助结构传入 GCS 构造器
`0x719c3330`（调用点 `0x719e11ee`）。

`0x719e1c40` 先查询已缓存结构，再经 `pe_factory_coordsys` 取
引擎句柄并尝试匹配已有结构。需要新建辅助结构时，在
`0x719e1d6a` 调用 `0x719bab40`，传入引擎句柄和原始代码。
四条域串由该构造器统一初始化为空。正代码或等价对象的缓存命中
分支会复用已有结构，因此初值结论只覆盖新建分支。缓存内容是否可
通过其他入口填充仍待核对。本轮未在 ArcMap 或 QGIS 中人工验证。

### PRJ 字符串工厂的域串

Geometry.dll 10.1.0.3035 的入口 `0x719e0570` 先调用
`wcstombs` 转换输入，于 `0x719e05cd` 调用
`pe_hvcoordsys_from_prjstring`（跳板 `0x719f3084`，IAT
`0x71a10d3c`）。解析成功后取得水平坐标系句柄，并在
`0x719e06b0` 把该句柄传给辅助结构查找函数 `0x719e1e40`。

查找函数按 `pe_projcs_p` 的结果分别用 `pe_projcs_eq` 或
`pe_geogcs_eq` 匹配缓存句柄。命中时增加现有辅助结构引用计数。
未命中时，`0x719e1ef6` 用句柄与代码 `-1` 调用
`0x719bab40`，将 Alias、Abbreviation、Remarks、Usage
初始化为空，再登记结构。调用方分别于 `0x719e06e3` 和
`0x719e0713` 将返回的结构传给 PCS 和 GCS 构造器。

因此在该 PRJ 导入入口的新建分支，解析出的引擎句柄与四个域串
各自初始化。缓存命中时沿用已有域串，实际共享与后续编辑仍待
运行核对。本轮未在 ArcMap 或 QGIS 中人工验证。

### Define 对现有辅助结构的写入

Geometry.dll 10.1.0.3035 的 GCS Define 从编辑接口 this+0x90
取得辅助结构（`0x719c02fb`），PCS Define 从 this+0x38
取得辅助结构（`0x719d5d86`）。换算为完整对象分别为
+0xb8 和 +0x68。在成功建立新引擎句柄的分支中，两者都
直接更新原结构的 +0x14 句柄、清零 +0x18 并将 +0x24 置为
-1，然后对非空字符串参数执行赋值。对应指令区间为
`0x719c04b2–0x719c0525` 与 `0x719d606f–0x719d60e6`。
在这两条入口中没有看到写入前按引用计数复制辅助结构的分支。

这说明如果两个实例仍持有同一辅助结构，成功执行 Define 会直接
修改该结构中的域串。尚未在 ArcMap 10.1 中构造一对缓存命中的
实例并验证编辑查询和保存结果，也未在 QGIS 中人工验证。

### GCS Clone 共享域串与编辑接口的分离条件

GCS 完整对象 +0x10 的 IClone 虚表 `0x71a265dc`，槽 3 为
`0x719be3f0`。Clone 在 `0x719be41d` 调用复制构造器
`0x719c3610`。该构造器把源对象 +0xb8 的辅助结构指针直接
存到新对象 +0xb8（`0x719c381b–0x719c3821`），并通过
`InterlockedIncrement` 增加结构 +0x20 的引用计数
（`0x719c3863–0x719c3871`）。该步骤共享包含四条域串的结构。

需要结合 QueryInterface 解读上一节的 Define 原位写入。GCS 通过
关联 PCS 指针检查后，在 `0x719bc4e6–0x719bc528` 检查结构
+0x1c 和引用计数。+0x1c 为零且引用计数大于 1 时，调用
`0x719c2d10`。+0x1c 非零时，若与对象 +0xd0 不同，或相同但
引用计数大于 2，也进入该调用。PCS 在
`0x719d090c–0x719d094b` 有相同的判断，比较对象 +0x158，
进入 `0x719da150`。两个辅助函数通过内部服务虚调用接收
对象结构指针的地址，并随后释放原结构引用。下文核对了派生服务的虚调用实现。因此仅凭 Define 的函数体不能断定经正常
接口查询后编辑会传播到其他实例。未在 ArcMap 或 QGIS 中人工验证。

### 编辑前复制辅助结构的单例管理器

Geometry.dll 10.1.0.3035 在 `0x718bdac3–0x718bdad1` 将
线程状态 +0xc8 作为 COM 查询输出地址，查询 IID
`58AB2690-5981-11D2-BCDA-0000F875BCCE`。同版 esriGeometry.olb
TypeInfo 86 将其定名为 ISpatialReferenceSingletonManager。
`0x719dd32f–0x719dd34c` 的 IID 分派返回完整对象 +0x18。
派生管理器在 `0x719e2248` 为该偏移安装虚表
`0x71a2bc24`，槽 3 指向 `0x719e1af0`。

该槽接收辅助结构指针的地址，分配 0x28 字节，并在
`0x719e1b09` 用当前结构调用复制构造器 `0x719d0510`，
随后于 `0x719e1b0e` 替换指针。复制构造器逐项复制
+0x04/+0x08/+0x0c/+0x10 四条域串，通过 `pe_coordsys_clone`
复制引擎句柄，并把新结构的引用计数设为 1。这个槽是上一节
两类编辑接口触发分离、且派生管理器已就绪时的复制路径。
运行时服务可用性、失败行为与两实例保存结果仍待原生验证。
本轮未在 ArcMap 或 QGIS 中人工验证。

### GCS Assign 的域串来源

Geometry.dll 10.1.0.3035 的 GCS IClone 虚表 `0x71a265dc`
槽 4 为 Assign（`0x719be440`）。常规分支在 `0x719be584`
查询源对象的 ISpatialReference，然后在 `0x719be595` 调用
该接口的 +0x20 槽。GCS 对此 IID 返回完整对象 +0x18，
该接口虚表 `0x71a26614` 的 +0x20 指向 `0x719bf640`。
此方法通过输出参数返回接口 this+0xa0，即完整对象 +0xb8
的辅助结构指针。

Assign 在 `0x719be5b4–0x719be5dc` 比较源和目标的结构指针。
若不同，调用 `0x719c2d80` 释放目标旧引用，将源指针写入
目标完整对象 +0xb8，随后增加结构 +0x20 的引用计数。
因此在这个分支中四条域串随结构共享。目标带关联 PCS 时，
`0x719be47e–0x719be49d` 在获取源结构前返回 `E_FAIL`。
共享后的编辑行为见上一节的分离条件。尚未在 ArcMap 或 QGIS
中人工验证。
