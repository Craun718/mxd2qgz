## 紧邻字段及边界

- Map Load `0x793ff4d0`：读取持久化接口相对 `+0x268` 的 short 后，指令 `0x793fffb8..0x793fffd0` 在版本大于 5 时进入对象读取，准备 `+0x1bc`；`0x793fffd6..0x793fffe1` 请求 IID 数据 `0x79483174` 并调用导入的 `LoadObject`。本轮从 PE 直接读出 IID `{1B07790D-38C5-11D0-92D2-00805F7C28B0}`；既有 10.1 类型库身份见 [图例族记录](arcmap-10.1-legend-family.md)，为 `IGeometry`。本入口支持的 23..=51 版本均经过此槽。
- 成功后 `0x793ffff5..0x79400001` 对该槽是否非空设置 `+0x1b4`；再于 `0x79400007..0x79400018` 读取 `+0x1c4`，请求 IID `{E4240307-DD41-11D2-B868-00600802E603}`，即既有类型库记录中的 `IBorder`。`0x79401850` Save 侧在 `+0x268` 之后顺序写 `+0x1bc` 和 `+0x1c4` 两个 SaveObject，和读侧对应。
- 这些证据确认第一个槽请求几何接口，尚不能证明其具体业务用途、具体几何类或非空实例的对象体与长度；`+0x1b4` 仅可确定由非空状态置位，不应据此命名业务属性。也不能从保存值推断运行期间的实际对象。
- 参考样本以 Map 根及共享键表连续读取，照明后定长字段止于 `/Maps:0x24ff4`；其后 16 字节全零，按已建立的对象流空标记规则，几何槽止于 `0x25004`。这只是辅助字节对位，不证明全部文件均为空，也不证明后续对象的完整布局。
