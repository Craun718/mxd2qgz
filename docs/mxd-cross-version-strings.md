# 跨 MXD 版本的 AfCore 字符串规则（2026-11-23）

本记录闭合 `TODO.md` 中「其他 MXD 版本的字符串规则」。结论只覆盖
ArcMap 10.1 目标读取链实际使用的 AfCore `String::Read/Write` 基础布局；
不把每一个对象类中的字符串字段都自动视为已定位。

## 证据

- ArcMap 10.1.0.3035 `AfCore.dll`，SHA-256
  `031858c414c0105b3b978c754f3d0f31ba1d98f15d44ff15b1589c9adcc47c17`。
  `String::Read` 为 `0x68ab46f0`，`String::Write` 为 `0x68ab4680`。
  读侧先读 4 字节回调长度，再读对应缓冲；写侧把码元数换算为
  `len * 2 + 2`，前缀取低 31 位，正文包含终止零。原生读侧不检查短读
  是否等于声明长度；Rust 的严格读取器有意拒绝短读。
- ArcMap 10.8.0.12790 `AfCore.dll`，SHA-256
  `560be16e0a99b9de4599f8241c421bddf0dcc8b26509f584074dea53b0ac4aae`。
  历史原生研究定位 `String::Read` `0x10055200`、`String::Write`
  `0x10055190`，其 4 字节长度、`len * 2 + 2`、短读和终止零规则与 10.1
  相同。来源见 [10.8 字符串记录](mxd-10.8-version-write-boundary.md) 所引的
  原生版本流研究。
- 10.1 保存版本表覆盖索引 0..5，即 8.3/9.0/9.2/9.3/10.0/10.1。版本索引由
  `AfStreamGetDocumentVersion` 取得，但 `String::Read/Write` 没有
  `esriArcGISVersion` 参数、没有文档版本接口查询，也不按版本跳转不同字段序。
  因此这六种由同一 10.1 写入器产生的文档使用同一字符串基础布局。
- [介质样本汇总](mxd-install-media-samples-20261117.md) 的实际 `/Version`
  覆盖 8.1/10、9.2/14、9.3/16、10.0/18、10.1/19；10.1 与 10.8 两组介质共
  102 份不同文件均可按同一头部读取。[10.1/10.8 交叉运行](mxd-10.8-version-write-boundary.md#101-与-108-头部交叉读取运行验证)
  又在原生 AfCore 执行下覆盖 154 组头部，10.1 读取器接受两版介质中
  short ≤19 的已知版本，10.8 读取器接受其全部已测索引。

## 结论与边界

在 ArcMap 10.1 目标范围内，跨 8.1 至 10.8 已观察文档的字符串基础规则不再按
MXD 版本分叉：同一个 4 字节长度加 UTF-16LE 载荷格式适用，版本差异应在调用点的
字段版本门和对象类布局中处理。若未来发现独立产品线或外来写入器，应作为新证据
重新核对，不能由本结论外推。

Rust 的 `read_string_10_1` 与 `read_string_10_8` 仍保留版本化名称，以标记证据来源；
新增契约测试 `version_10_1_and_10_8_writer_subsets_match` 固定两者对正常和异常输入
的游标及错误种类一致。该测试不替代原生短读行为，也不证明具体 MXD 字段归属。
